# مدل کنترل دسترسی Profile

## نقش‌ها

فقط `IT_ADMIN`، `FINANCE_ECONOMIC_ADMIN` و `USER` شناسه امنیتی‌اند. دو مدیر
سطح بالا دسترسی کامل و برابر دارند و grant کارخانه ذخیره نمی‌کنند. `USER` فقط
از grant صریح دسترسی می‌گیرد. `job_title` صرفاً داده نمایشی است.

## grant کارخانه

هر grant زوج مشخص دامنه/کارخانه، ماژول و سطح‌های مجوز سلسله‌مراتبی است.
شناسه کارخانه باید در رجیستری canonical وجود داشته و برای تخصیص جدید فعال باشد.
شناسه ناشناخته، کارخانه غیرفعال، scope/module/permission ناشناخته و payload
ناقص در سرور رد می‌شود.

## منبع کارخانه‌های UI

`ProfileDataStore` تنها منبع زمان اجرای Profile است. کشف داده‌های عملیاتی یک
import یک‌طرفه و اتمیک به همان JSON است. view model فقط فیلدهای عمومی کارخانه
فعال را به modal فارسی/RTL می‌دهد. JavaScript نام یا ID پیش‌فرض ندارد و نام
نمایشی را همراه code نشان می‌دهد ولی ID canonical را ارسال می‌کند. در نبود
کارخانه، پیام صریح «هیچ کارخانه‌ای در داده‌های سیستم ثبت نشده است.» نمایش داده
می‌شود.

## ایجاد کارخانه (Phase 6.7)

فقط دو نقش سطح بالای هم‌رتبه می‌توانند از Profile کارخانه بسازند. API هویت actor
را از نشست و سپس از JSON canonical بازخوانی می‌کند؛ `job_title`، grant یا هر
شناسه actor ارسالی مشتری هیچ اختیاری ایجاد نمی‌کند. کارخانه جدید برای هر دو مدیر
بدون grant ذخیره‌شده فوراً قابل دسترسی است و برای `USER` تا زمان grant صریح بسته
می‌ماند.

مفاهیم Official Admin، Factory Admin، Office Staff، Factory Staff و مجوز مشتق
از عنوان شغلی منسوخ‌اند. ایجاد کارخانه در Phase 6.7 کامل شده است؛ ویرایش،
غیرفعال‌سازی و حذف کارخانه و ویرایش عمومی کاربران همچنان کار آینده است.

## انتشار سراسری رجیستری (Phase 6.8)

`FactoryService` مرز مشترک همه ماژول‌های کارخانه‌محور است. مدیران هم‌رتبه همه
کارخانه‌های فعال را به‌صورت ضمنی می‌بینند؛ USER تنها گزینه‌ای را دریافت می‌کند
که grant همان factory/module/action را دارد. همین تصمیم در backend هر read و
mutation دوباره کنترل می‌شود و شناسه URL، payload یا session ناشناخته/غیرفعال/
غیرمجاز هرگز به کارخانه نخست یا F1 برنمی‌گردد. جزئیات سطح‌ها و initialization
در `docs/factory-integration-inventory.md` ثبت شده است.

## سلسله‌مراتب مجوز و مدیر بصری دسترسی (Phase 7.1)

سطح‌های مجوز canonical به‌ترتیب `NONE < READ < WRITE < MODIFY` هستند و به
`[]`، `[READ]`، `[READ, WRITE]` و `[READ, WRITE, MODIFY]` تبدیل می‌شوند. WRITE
همیشه READ و MODIFY همیشه هر دو سطح پایین‌تر را شامل می‌شود؛ مقایسه backend نیز
بر اساس همین سطح مؤثر است، نه ترتیب آرایه ورودی.

ویرایشگر تولیدی USER بخش جداگانه «دسترسی سراسری» و کارت‌های بازشونده کارخانه
دارد. هر ردیف ماژول دقیقاً یک selector با گزینه‌های «بدون دسترسی»، «فقط مشاهده»،
«ثبت اطلاعات» و «ویرایش کامل» دارد. ماژول سراسری زیر کارخانه مصنوعی قرار
نمی‌گیرد و کارخانه‌های قابل افزودن فقط از رکوردهای فعال رجیستری canonical می‌آیند.
grant تاریخی کارخانه غیرفعال قابل مشاهده و حذف است ولی برای افزودن عرضه نمی‌شود.

parser قطعی grantهای canonical را به یک سطح مؤثر برای هر scope/module تبدیل
می‌کند و serializer قطعی، NONE را حذف و سایر سطح‌ها را با ترتیب پایدار به schema
موجود برمی‌گرداند. مدیران هم‌رتبه به‌جای selector پنل «دسترسی کامل سامانه»
می‌بینند و grant زائد برای آنها تولید نمی‌شود. پاک‌سازی frontend در فازهای بعد
باید الگوی «کارت کارخانه ← ردیف ماژول ← دقیقاً یک selector» را حفظ کند.
