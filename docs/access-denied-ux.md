# تجربه کاربری 403 / دسترسی محدود — Phase 8.4

## معماری پاسخ

خطاهای مجوز همچنان در همان decoratorها و `FactoryService` تولید می‌شوند و status
آنها **403** باقی می‌ماند. handler سراسری برنامه فقط نمایش پاسخ را انتخاب می‌کند:

- درخواست عادی صفحه، template مستقل `errors/403.html` را با متن فارسی و جهت RTL
  و همان status 403 دریافت می‌کند؛ redirect خودکار انجام نمی‌شود.
- مسیرهای `/api/`، درخواست دارای JSON، XHR و clientای که صریحاً
  `Accept: application/json` می‌فرستد، پاسخ JSON استاندارد شامل `success: false`،
  `error: forbidden` و پیام عمومی فارسی دریافت می‌کنند. بنابراین `fetch` مجبور به
  parse کردن HTML نیست.
- endpointهایی که پیش از handler پاسخ JSON اختصاصی و 403 می‌سازند، قرارداد موجود
  خود را حفظ می‌کنند.

## بازیابی امن و عدم افشای اطلاعات

صفحه دکمه «بازگشت» دارد و فقط در صورت وجود history مرورگر از آن استفاده می‌کند؛
در غیر این صورت لینک همان دکمه مقصد امن سمت سرور است. مقصد با
`first_accessible_endpoint` و grant مؤثر انتخاب می‌شود: میز کار در صورت دسترسی،
سپس نخستین ماژول واقعاً قابل دسترس، و در نبود هر grant مسیر خروج امن. در نتیجه
`desk = NONE` هیچ لینک میز کاری تولید نمی‌کند و مقصد ممنوع حلقه redirect نمی‌سازد.

متن پاسخ عمومی است و نام کارخانه، مسیر درخواست، سطح لازم، نقش‌ها، grantها و پیام
exception را نمایش نمی‌دهد. به‌ویژه denial کارخانه‌ای نام کارخانه پنهان را فاش
نمی‌کند. نام ماژول نیز از URL حدس زده نمی‌شود.

## مرز احراز هویت، frontend و audit

کاربر بدون نشست همچنان به login redirect می‌شود؛ صفحه جدید فقط برای کاربر
احراز‌شده‌ای است که authorization او رد شده است. logout، تغییر اجباری گذرواژه و
سایر عملیات امنیت نشست grantable نیستند و handler آنها را تغییر نمی‌دهد. پاسخ
JSON پیام قابل نمایش در toast/هشدار موجود را فراهم می‌کند و صفحه فعلی را جایگزین
نمی‌کند. handler هیچ business audit event تازه‌ای ثبت نمی‌کند؛ سیاست audit فاز 9
نیز در این فاز آغاز نشده است.

Phase 10 می‌تواند فایل‌های frontend را جابه‌جا کند، اما باید status 403، تفکیک
HTML/JSON، RTL و سیاست عدم افشا را حفظ کند. Phase 12 باید عدم بازگشت صفحه پیش‌فرض
Werkzeug را در denialهای عادی production بازآزمایی کند.
